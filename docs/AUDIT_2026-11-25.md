# Audit of WTP Question Rank, 25 November 2026

*Scope: this repo at `a891c45`, the live site (read-only requests), and a local copy seeded with 865 simulated votes
from 18 codes. Fixes are on branch `claude/busy-franklin-ct2lna`; nothing was pushed to `main`, and no Cloudflare
setting, secret or production row was touched.*

## Verdict

The site is sound for Round 1 and can feed the pre-registered analysis as designed, but it has one hole in the
pre-registered sensitivity analysis and it cannot run Round 2 as planned. The vote log is append-only in the database
itself, the export matches `RoundExport`, question ids do not reach the voting page, and the guards, CSP and admin
login hold up. The hole: a voter can change a pre-leaderboard vote after opening the leaderboard, and the export still
marks that vote `after_board = 0` (finding 1). Round 2 fails three ways at 420 questions: the pairing step needs about
380 ms of CPU against a 10 ms limit, two queries exceeded D1's 100-parameter limit (fixed), and `after_board` is kept
per voter, not per round (findings 2, 3 and 6). Seven low-risk defects are fixed in seven commits; `npm test`
(135 tests) and `npm run typecheck` pass. Everything that changes what voters see or do is a proposal below.

## How the audit was done

- **Read:** `CLAUDE.md`, `README.md`, `DEVIATIONS.md`, `docs/NEXT_STEPS.md`, `docs/SPEC.md`,
  `PREREG_Human_vs_LLM.md`, every file in `src/worker/` and `src/web/`, all four migrations, `src/rating/config.ts`,
  `src/rating/pairs.ts`, and the input and rater-flag parts of `analysis/analyze.ts`.
- **Ran:** `npm test`, `npm run typecheck`, `npm run build`, the local server, a script that cast 865 votes through
  the API, Playwright at 1280, 375 and 320 pixels in light and dark, axe-core 4 on every page state, and a Node
  benchmark of the rating fit and pairing at 36, 204 and 420 items.
- **Live site:** GET requests to the public pages, static files, `/api/config`, `/api/me` and `/admin`, and one POST
  to `/api/redeem` with an empty body and no Origin (refused with 403 `bad_origin`; it wrote nothing).
- **Source status.** Cloudflare limits were read on 25 November 2026 by a subagent that fetched each docs page and
  relayed the quoted lines; I did not open those pages myself, so pull them before relying on a number. The W3C
  Recommendation page could not be opened from this environment. The WCAG wording below comes from W3C's source files
  on GitHub (the editors' `main` branch), so each WCAG citation is marked [[UNVERIFIED]] against the published text.
- **Not done:** no sign-in, vote or export on the live site; no reading of production D1; no load test on Cloudflare
  itself. CPU figures are Node timings on this machine, not Workers measurements.

## Findings, ranked by severity

### High

**1. A pre-leaderboard vote can be changed after the voter opens the leaderboard, and it still counts as
pre-leaderboard. Proposed (the export part is Fixed, `cb9dd93`).**
- *Where:* `src/worker/voter.ts:476` (`/correct`), `src/worker/voter.ts:485` (only test: is it the newest batch),
  `migrations/0004_vote_corrections.sql:43` (`votes_effective` keeps the first vote's `after_board`),
  `src/web/vote.ts:301` ("Back to this batch").
- *What goes wrong and when:* a voter finishes the batch that takes them to 20 votes. The "Batch done" screen offers
  the leaderboard link and "Back to this batch". They open the leaderboard, press the browser's Back button (the page
  comes back from the browser's cache with the batch intact), go back into the batch and change answers. The server
  accepts each change because no newer batch exists. Those votes were cast with `after_board = 0`, so PREREG §8's
  "votes cast before the voter first opened the leaderboard" analysis includes answers given after the board was
  seen. The same route works from a second tab.
- *Size:* at most the 10 pairs of one batch per voter, once per voter per round, unless they repeat it each batch
  (every later batch is already `after_board = 1`, so only the batch that crosses 20 matters).
- *Fixed:* `corrections.csv` now carries `vote_after_board` and `correction_after_board`. A row reading 0 then 1 is
  such a change, so the analysis can drop or re-run those votes.
- *Proposed (needs your yes; it narrows the Back feature you approved, so it is a logged deviation):* refuse a
  correction when the vote has `after_board = 0` and the voter has since opened the board, with the existing
  "That batch is finished" message. Five lines in `/correct` and one test.

**2. Round 2 with every published question cannot run on the Workers Free plan. Proposed (decision needed).**
- *Where:* `src/worker/voter.ts:160`–`162` (a full fit with standard errors on every new batch),
  `src/rating/pairs.ts:80` (every unordered pair is a candidate: 88,000 at 420 items), `src/worker/data.ts:154`
  (a fit on every leaderboard view).
- *Measured (Node, warm):* at 36 items a new batch costs about 1 ms to fit and 1 ms to select. At 420 items it costs
  about 211 ms to fit and 173 ms to select, and a leaderboard view costs about 93 ms. The Free plan allows 10 ms of
  CPU per request (Workers limits page, read 25 Nov 2026).
- *When:* the first `GET /api/batch` of a 420-item round. Round 1 is not affected.
- *Fix options:* (a) Workers Paid, which lifts the CPU limit; (b) run Round 2 as several rounds of about 70 questions
  (one per unit); (c) a separate, cheaper pairing module for Round 2 only. `pairs.ts` is frozen and is not changed by
  any of these. I recommend (b): it also keeps each voter's task to comparable questions and needs no new spend.

**3. Two queries bound one parameter per question and would fail above 100 questions. Fixed, `e4f47b0`.**
- *Where:* `src/worker/voter.ts:42` (`questionRows`, used by the leaderboard), `src/worker/admin.ts:137` (item
  loader).
- *What went wrong and when:* D1 allows 100 bound parameters per query (D1 limits page, read 25 Nov 2026). The
  leaderboard and the item loader each sent one `?` per question, so loading or showing a set of more than 100
  questions would error. Local D1 does not enforce the limit, so no test could have caught it.
- *Fix:* ids now go out in chunks of 90. A test loads 130 questions.

**4. Plain `http://` was served, so a typed code could cross the network unencrypted. Fixed, `a05f000`; one owner
step proposed.**
- *Where:* `src/worker/guards.ts:30`.
- *What went wrong and when:* `http://wtpquestionrank.spiffyspaceman.com/api/config` answered 200 on the live site
  today. A voter who typed the address without `https` got a working page; the browser then sent the code in a POST
  over http before the Worker refused it for the wrong Origin. Invite links are https, so only hand-typed addresses
  were exposed.
- *Fix:* GET and HEAD over http redirect to https (308); other methods get 400 before the body is read by any route.
- *Proposed (Cloudflare setting, yours):* turn on **Always Use HTTPS** for the zone so the redirect happens at the
  edge too.

### Medium

**5. Two corrections of one vote at the same moment could leave the rating cache wrong. Fixed, `fb0ff9e`.**
- *Where:* `src/worker/voter.ts:476` onward.
- *What went wrong and when:* two devices correct the same vote together. The second request read the old winner,
  saw "winner unchanged", skipped the `pair_counts` update and then appended a correction that did change the winner.
  The leaderboard then disagreed with the log until someone pressed Rebuild caches.
- *Fix:* the cache update is always sent; its size is computed inside the transaction and is zero when nothing
  changed. A test fires both requests together and compares the cache with a rebuild.

**6. `after_board` is tracked per voter, not per round. Proposed (before Round 2).**
- *Where:* `migrations/0001_init.sql:81`, `src/worker/voter.ts:396`, `src/worker/voter.ts:614`.
- *What goes wrong and when:* a voter who opened the Round 1 board has every Round 2 vote marked `after_board = 1`
  from the first one, although the Round 2 board is locked to them until 20 Round 2 votes. The flag then says nothing
  in Round 2.
- *Fix:* migration 0005 with a `(voter_id, round_id, seen_at)` table; the vote insert and the export read that.
  Round 1 data is unaffected.

**7. No sign-out, with a 90-day session. Proposed (voter-visible, needs your yes).**
- *Where:* `src/worker/auth.ts:8`; no sign-out route exists; `src/web/home.ts` sends a signed-in browser straight to
  `/start`.
- *What goes wrong and when:* a student signs in on a school or library computer. The next person who opens the
  site on that computer within 90 days is that student and can vote as them.
- *Fix:* `POST /api/signout` that deletes the session row and clears the cookie, and a "Sign out" link on `/start`.

**8. Static files were revalidated on every page view, each through the Worker. Fixed, `a05f000`.**
- *Where:* `src/worker/guards.ts`, `wrangler.jsonc:18`.
- *What went wrong and when:* the live site served hashed files and fonts with `max-age=0, must-revalidate`.
  With `run_worker_first` every one of those checks is a Worker request that counts toward the Free plan's 100,000 a
  day (static assets billing page, read 25 Nov 2026). A voting page view cost 6 Worker requests before any API call.
- *Fix:* `/assets/*` is `immutable` for a year (names carry a content hash); `/fonts/*` is kept 30 days. Pages still
  revalidate.

**9. The unchosen question fades to 45% and fails contrast. Proposed (changes what voters see).**
- *Where:* `src/web/styles.css:180`.
- *What goes wrong and when:* after a tap, the other card's text measures 2.07:1 in light mode and 2.35:1 in dark
  (axe-core), against 4.5:1 in WCAG 1.4.3 [[UNVERIFIED]]. The voter is still deciding at that point: reasons and
  Next come after. A faded card is hard to re-read, which nudges people to keep their first tap.
- *Fix:* fade the border and background, keep the text at full ink, or raise the opacity to about 0.75.

**10. Single-key shortcuts cannot be turned off. Proposed (voter-visible).**
- *Where:* `src/web/vote.ts:322` (S skips at once; C, 0–9 also act).
- *What goes wrong and when:* a voter using speech input, or one who bumps a key, skips a pair or toggles a reason.
  WCAG 2.1.4 [[UNVERIFIED]] asks for a way to turn such shortcuts off or remap them.
- *Fix:* a "Keyboard shortcuts" checkbox in the Keys section of `/start`, remembered in the browser.

**11. Keyboard focus was lost after every vote, and Enter on a link cast a vote. Fixed, `6e3d60d`.**
- *Where:* `src/web/vote.ts:166`, `src/web/vote.ts:318`.
- *What went wrong and when:* pressing Next hid the Next button, so focus fell to the top of the document and a
  keyboard or screen-reader user had to tab back down for each of ten pairs. And with a side chosen, pressing Enter on
  the "WTP Question Rank" or "Leaderboard" link sent the vote instead of following the link (confirmed in the
  browser).
- *Fix:* focus moves to the pair counter, which is neutral between A and B and reads out "Pair 3 of 10"; Enter on a
  link follows the link.

**12. The build runs the tests but not the typecheck. Proposed (Cloudflare build setting, yours).**
- *Where:* `README.md:157`.
- *Fix:* change the Workers Builds command to `npm ci && npm run typecheck && npm test && npm run build`.

**13. The exports are not a full backup. Proposed (feature 1 below).**
- *Where:* `src/worker/exports.ts`.
- *What goes wrong and when:* `batches` and `batch_pairs` (seed, position, pairing reason, issue time), the first
  winner of a corrected vote (only in `corrections.csv`), `admin_audit` and the snapshots are in no export. Time
  Travel keeps 7 days on Free. If the database were lost in week three, the pairing audit trail would be gone even
  with every weekly export in hand.

### Low

**14. A paged export could list a vote whose voter was missing. Fixed, `d3ad4ac`.** `src/web/admin.ts:141`. The
voter list was read before the vote pages, so a voter whose first vote landed mid-export was absent from `voters`.
The list is now read last.

**15. Chart bars showed no keyboard focus. Fixed, `6e3d60d`.** `src/web/styles.css:319`–`321`. The chart turned the
page's focus outline off and bars only changed opacity from 0.85 to 1.

**16. The voting and admin pages had no level-one heading. Fixed, `6e3d60d`.** `src/web/vote.html`,
`src/web/admin.html`. Screen-reader users navigate by headings; the voting page now has a hidden "Vote" heading.

**17. A skipped pair that is later voted on counts as two trials. Proposed.** `src/worker/voter.ts:207`. The swapped
repeat then becomes eligible one trial early (19 real trials apart, not 20). Fix: count each pair once. It touches
when a repeat appears, so it needs your yes and a line in `DEVIATIONS.md`.

**18. Students' votes help choose the pairs adults see. Proposed (document only).** `src/worker/voter.ts:162` fits
the `all` pool for pairing. PREREG §4 does not say which pool feeds the pairing. It does not bias the adult fit, but
it should be written down as a clarification.

**19. The wrong-code limit is 10 a day per IP address.** `src/worker/auth.ts:9`. A school behind one address shares
the 10; a class typing codes by hand could lock the school out until midnight UTC. Invite links avoid typing. Fix if
it happens: raise the limit, or count per address and code prefix.

**20. The leaderboard's reasons query reads the whole round's votes on every view.** `src/worker/voter.ts:637`. My
estimate, not a measurement: 30,000 to 50,000 rows read per view at 5,000 votes, against 5 million a day on Free
(D1 pricing page, read 25 Nov 2026), so roughly 100 to 150 leaderboard views a day at that size. Fine for Round 1.
Fix when needed: a small `reason_counts` cache updated with each vote, like `pair_counts`.

**21. When another device answered a pair first, the page shows this device's answer.** `src/web/vote.ts:272`,
`src/worker/voter.ts:431`. The server keeps the first answer and replies `duplicate`; the page ignores that. Reload
shows the truth. Fix: on `duplicate`, reload the batch.

**22. After the last round closes, `/start` says "No round yet".** `src/worker/data.ts:14` returns only open or
frozen rounds. Fix: say "Voting has ended."

**23. Small items, no action needed now.**
- Turnstile: the hostname is checked (`src/worker/turnstile.ts:27`); the `action` field and an `idempotency_key`
  are not used. Token reuse is caught by Cloudflare only eventually (Turnstile docs, read 25 Nov 2026). The throttle
  and 60-bit codes make this harmless.
- `GET /api/batch` and `GET /api/leaderboard` change state (issue a batch; set `board_seen_at`). With a `SameSite=Lax`
  cookie, a link from another site could trigger either. The effect is a batch issued early or the board marked seen
  for a voter who is in fact shown it.
- `/api/redeem` tells a revoked code from a wrong one. Only the holder of a real code learns anything.
- `rating_snapshots` and `admin_audit` grow without pruning; both are tiny.
- The comment at `migrations/0001_init.sql:75` says SHA-256 where the code uses HMAC-SHA256. The file is frozen;
  the README is right.
- Admin tables scroll sideways on a phone without keyboard access to the scroll region, and the votes-per-day table
  has an empty header cell (axe-core).
- The head-to-head chart's small count text measures 4.37:1 on its strongest blue cell, just under 4.5:1.

## What held up

- **Append-only is enforced by triggers**, not by convention, on votes, skips, reasons, corrections and the audit
  log, and `test/worker/schema.test.ts` checks that they fire.
- **Races:** batch creation, double submits, freeze-during-vote and revoke-during-vote are each closed inside one D1
  transaction and tested (`test/worker/races.test.ts`).
- **The voting page gets stem and bullets only.** A test asserts that no id, cycle, unit, level or number key is in
  the batch response. Tie order on the board is hashed so it cannot leak id order.
- **Privacy:** no name, email, IP or user agent is stored. The attempt key is a salted hash that rotates daily.
  The Other note is capped at 20 words and 200 characters, stripped of control characters, kept out of every voter
  response, and made formula-safe in CSV.
- **Admin:** Access in front, and the Worker checks signature, issuer, audience, expiry and not-before itself, which
  is the list Cloudflare's validation page gives (read 25 Nov 2026). The fallback secret is refused while Access is
  configured.
- **Headers on the live site:** CSP limited to self and Turnstile, `frame-ancestors 'none'`, HSTS, `nosniff`,
  `no-referrer`, `noindex`, and `no-store` on every `/api` and `/admin` response. No analytics beacon is in the HTML.
- **Weight:** the voting page is 4 KB of HTML, 4.5 KB of CSS and about 4 KB of script compressed, plus one 22 KB
  font. Nothing third-party loads after sign-in.
- **Cost at Round 1 size:** a vote is about 13 D1 statements in 6 calls, a `db.batch()` counts as one query against
  the 50-per-request limit (D1 limits page, read 25 Nov 2026), and the fit takes about 1 ms.

## Design review (with the frontend-design skill)

The design has a point of view and keeps to it. One serif at one weight, a burgundy rule across the top, italic
for labels, and no bold or capitals read as a printed hearing packet, which suits the subject. Size and colour carry
the hierarchy without help. I would not restyle it. The points below are where it works against the voter.

- **Voting, phone (375 px).** Two long questions stack to about 2.3 screens, and the pick buttons sit below both.
  Tapping a card chooses it, so the task still works, but Question A is always on top. On a phone "left" means
  "first read", a stronger position effect than left-versus-right on a desktop, and the log cannot tell the two
  layouts apart (feature 7). I advise against a sticky pick bar: it would let a voter choose before reading B.
- **Voting, after a pick.** Finding 9. Also, when two reasons are chosen the other eight pills dim to 45% and look
  the same as the faded card, so "full" reads as "broken". A line such as "Two chosen" would say it.
- **Voting, Back and Forward.** A changed answer is lost without a word if the voter presses Forward and not Next.
  A short "Next saves the change" beside Forward would do.
- **Loading.** `/vote` and `/board` show only the masthead until the first fetch returns. On a slow connection that
  is a blank page. A one-line "Loading the next pairs" is enough.
- **Leaderboard, desktop.** The top question is right: one big number, the text in full. The Top 10 column then
  clamps each stem to two lines in a narrow column beside the charts, so nine questions each show eight words.
  Giving the list the full width and putting Explore below it would let the questions, the subject of the page, be
  read.
- **Leaderboard, copy.** `statLine` joins facts with middle dots (`src/web/board.ts:88`), and "Top question" sits as
  a label over a card that already says "#1". Both are template habits the rest of the site avoids.
- **Leaderboard, phone.** It reflows cleanly at 320 px with no sideways scroll. The page is about 12 screens long;
  the charts sit between the Top 10 and the full list, so a voter looking for a question scrolls past them.
- **Sign-in.** Clear and short. The error for a failed check says "Reload the page", but the widget already resets
  itself; "Try again" is truer.
- **Admin.** One long page. With 50 Other notes shown, the Raters table, which is what you check most, sits about
  four screens down. Put Raters above Reasons, or fold the notes.
- **Touch targets.** Every voting control is at least 40 px tall, above the 24 px in WCAG 2.5.8 [[UNVERIFIED]].
  Back (37×40) and the pills (40 tall) are under the 44 px of the stricter 2.5.5 [[UNVERIFIED]].
- **Motion.** None, and `prefers-reduced-motion` is honoured anyway.
- **Dark mode.** Works on every page; contrast holds except for finding 9.

## Study design fit

1. **Post-board corrections** (finding 1) are the one place the site lets data into a pre-registered subset that
   the definition excludes.
2. **Logged deviations are logged honestly.** The home-page guidance, reason pills, Other, Back and the leaderboard
   details are each in `DEVIATIONS.md` with their likely effect.
3. **`server_ms` runs from the previous answer, so reasons, Back trips and breaks all lengthen it.** The 20-second
   "too fast" flag can only fire less often than registered. That is logged.
4. **The pills name criteria before the vote is sent.** A voter picks, reads nine named qualities, and can still
   change the pick. The pills can therefore shape the vote they are attached to, not only later ones. Logged, but
   the size of the effect is unknowable from this design because no voter votes without them.
5. **The data gate needs at least 540 adult first votes** (36 items × 30 comparisons ÷ 2) spread evenly, from 15
   raters with 20 each. Warm-up balances items across all voters, students included, so the adult count per item can
   lag the overall count.
6. **The owner's test code `Other 04` holds 20 votes in Round 1** until it is revoked (already step 5 in
   `docs/NEXT_STEPS.md`).

## The weakest part of the site, and the strongest case against the current design

**The weakest link is that the study's own comparison is no longer like for like, and the site cannot measure how
far apart the two arms have drifted.** The LLM judges saw the hearing-format paragraph, the criterion, and two
questions, and gave one forced choice. A human voter now reads judging guidance paraphrased from CCE's Toolkit
first, picks, is shown nine named qualities, may revise the pick, may go back and revise again, and after 20 votes
sees the crowd's ratings, win shares and reasons, with year and unit attached. Each step is logged in
`DEVIATIONS.md`, and §8 covers the leaderboard. But the guidance and the pills apply to every human vote from the
day they shipped, so there is no within-study contrast to estimate their effect, and finding 1 means even the
pre-board subset is not clean.

**The strongest opposing case runs as follows.** Rule: a validation study should change one thing between its arms.
Facts: this one now differs in instructions, in prompts shown at the moment of choice, in the ability to revise,
and in exposure to other raters' answers. Conclusion: whichever way ρ lands, a reader can attribute it to the
instructions and not to the method. A high ρ can be read as "people told what strong questions do, and shown named
criteria, agree with a model that applies the same textbook criteria"; a low ρ can be read as "the people were
steered and the model was not". The same critic would add that the leaderboard is the incentive that makes
invitees vote, and it is also the largest contaminant, so the design trades data quality for data quantity at
exactly the 20-vote mark where the gate starts counting a rater.

**This imbalance is structural; it cannot be argued away, only managed.** Three ways, in order of value:
1. Re-run method A with the human arm's guidance and the nine reasons in the packet, as a registered addendum, and
   report ρ against both LLM runs. That restores a like-for-like pair without touching a single human vote.
2. Close the post-board correction route (feature 2) so the §8 pre-board subset means what it says.
3. Report the primary result on votes cast before the guidance deploy as well, if there are enough. Today there are
   not (20 test votes), so say so in the write-up instead of leaving it for a reviewer to find.
